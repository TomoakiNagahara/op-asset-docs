# 2026-05-14 Agent Review 2

## Scope

This note records a second documentation mistake made during the same work session.

The mistake was adding sensitive deployment-specific header details to a document that may be published.

## What The User Pointed Out

The user pointed out that secret or deployment-specific verification key names and values must not be included in public documentation.

Even when a secret value itself is not described as a password, the exact header name, token name, or verification key name can still be sensitive because it reveals part of the deployment's protection mechanism.

## Incorrect Agent Behavior

The agent wrote a concrete verification header name into the review document.

That was wrong because:

- Public documentation should not expose private deployment mechanisms.
- Specific secret header names and token names reduce the security value of the verification layer.
- A review document should preserve the lesson without publishing implementation-specific secrets.

## Correct Direction

Use general terms instead of concrete secret names:

- origin verification mechanism
- trusted proxy verification
- deployment-owned secret header
- private verification token

Do not write the actual key name, header name, token name, or value unless the user explicitly says it is intended for publication.

## Lessons

[DOC-RISK] Do not include sensitive key names, header names, token names, or values in repository documents that may be published.

[DOC-RISK] Treat exact names of private verification mechanisms as sensitive, not only their values.

[DOC-GAP] Before writing incident or review documentation, classify whether each concrete identifier is public architecture, internal implementation detail, or secret deployment detail.

[DOC-FUTURE] Agent review documents should describe security lessons at the right abstraction level and avoid exposing details that would help bypass the deployment's trust boundary.
