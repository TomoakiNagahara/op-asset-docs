# 2026-05-14 Agent Review

## Scope

This note records a review of an incorrect agent response during work on `asset/config/_admin.php` and `asset/core/include/isAdmin.php`.

The original goal was to make admin detection work correctly in a production environment behind Cloudflare.

## What The User Pointed Out

The user clarified several important design constraints:

- `asset/core/include/isAdmin.php` is existing core behavior and was already working correctly.
- Core admin detection should stay simple.
- Core should compare one configured allowed IP address with `REMOTE_ADDR`.
- Cloudflare-specific handling belongs in local application or deployment configuration, not in core.
- The correct edit location for this issue was `asset/config/_admin.php` only.
- `HTTP_CF_CONNECTING_IP` can be spoofed and must not be trusted without an origin verification mechanism.
- Cloudflare IP ranges can change, so hardcoding them in source code is not an acceptable long-term assumption.
- In this deployment, a valid origin verification mechanism means the request came through the trusted proxy, and then the trusted proxy's client IP header is expected to exist.

## Incorrect Agent Changes

The agent made several bad changes before the direction was corrected:

- Modified `asset/core/include/isAdmin.php` even though the task should have been solved in `asset/config/_admin.php`.
- Added proxy and Cloudflare-specific logic to core, making a simple core function unnecessarily complex.
- Compared `HTTP_CF_CONNECTING_IP` directly before fully respecting the spoofing risk.
- Hardcoded Cloudflare IP ranges into source code.
- Added a generated local Cloudflare range file instead of first respecting the existing core boundary.
- Updated core documentation to describe the bad core behavior.

These changes were wrong because they moved deployment-specific behavior into core and expanded the responsibility of `isAdmin()`.

## Correct Direction

The corrected design is:

- Keep `asset/core/include/isAdmin.php` simple.
- Keep core documentation aligned with the simple core rule.
- Complete Cloudflare-specific behavior in `asset/config/_admin.php`.
- Use deployment-owned origin verification before trusting Cloudflare request headers.
- Set `OP::_ADMIN_IP_` to the current `REMOTE_ADDR` only when the verified trusted-proxy request carries an allowed client IP.

This preserves the core contract: core only compares `REMOTE_ADDR` with the configured admin IP.

## Lessons

[DOC-RISK] Do not change core code when a deployment-specific config file can solve the problem.

[DOC-RISK] Do not make a stable core function more complex to handle one deployment environment.

[DOC-RISK] Do not trust client-provided request headers unless the request has first been verified as coming from the trusted path.

[DOC-GAP] When a user asks to check a local override file such as `asset/config/_admin.php`, inspect the intended override boundary before proposing core changes.

[DOC-FUTURE] If trusted proxy handling becomes a framework feature, it should be designed as an explicit configuration contract rather than added ad hoc to `isAdmin()`.
