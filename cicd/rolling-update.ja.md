# ローリングアップデートの仕様

## 概要

ONEPIECE Framework は、ローリングアップデート方式です。

この方式では、Year が変わるとメインブランチも変わります。

例:

- `2025` から `2026`
- `2030` から `2031`

つまり、同じメインブランチを固定で使い続けるのではなく、年の切り替わりに合わせてメインブランチも次の年へ移行します。

## メインブランチの考え方

ONEPIECE Framework のメインブランチは Year ベースです。

branch 名そのものが、その時点のメインラインを表します。

そのため、年が変わると、メインブランチ名も次の年に変わります。

## 設定箇所

この設定は `asset/config/op.php` で管理します。

ここでは `_OP_APP_BRANCH_` を定義しています。

例:

```php
define('_OP_APP_BRANCH_', 2030);
```

`_OP_APP_BRANCH_` は、そのアプリケーション系統で使う基準 branch を表します。

## 年切り替え時のルール

`_OP_APP_BRANCH_` を変更する場合は、Git の branch 名も同じ値に変更します。

たとえば、

- `_OP_APP_BRANCH_` を `2030` から `2031` に変更する
- それに合わせて branch 名も `2031` に変更する

この 2 つは常に一致している必要があります。

## この仕様の意味

このローリングアップデート方式には、次の意味があります。

- メインラインが branch 名で明確になる
- 年ごとの移行を branch の切り替えとして扱える
- framework 設定と Git 運用を一致させられる

さらに、この方式には重要な運用上の意図があります。

- アップデートを意図的に遅らせることができる

すぐに次の Year へ移行したくない場合は、現在の Year branch に留まることで、更新タイミングを明示的に制御できます。

## なぜ branch 名を Year にするのか

branch 名を Year にしている理由は、見分けやすさだけではありません。

CORE や UNIT でも branch 名を Year で統一しているため、関連する repository 全体を同じ Year 系統で揃えることができます。

これにより、時間の経過によって発生する仕様変更の不一致に対応しやすくなります。

実際の意味は次の通りです。

- application は現在の Year branch に留まることができる
- CORE も同じ Year branch を使える
- UNIT も同じ Year branch を使える
- 異なる Year の仕様変更が意図せず混ざることを避けやすい
- 同じ Year 系統に揃えている限り、常に CI が通っている状態をキープしやすい

## まとめ

ONEPIECE Framework のローリングアップデート仕様は、次の通りです。

- メインブランチは Year ベースである
- Year が変わると、メインブランチも次の Year に変わる
- `asset/config/op.php` の `_OP_APP_BRANCH_` と branch 名は一致していなければならない
- Year ベースの branch にすることで、アップデートを意図的に遅らせることができる
- CORE や UNIT も同じ Year branch で統一することで、仕様変更の不一致を避けやすく、CI が通る状態を維持しやすい

たとえば、`_OP_APP_BRANCH_` を `2030` から `2031` に変更する場合、branch 名も `2031` に変更します。
